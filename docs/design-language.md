# زبان طراحی بهار — نسخهٔ 3.1

**وضعیت:** مرجع اصلی پیاده‌سازی  
**دامنه:** پنل عملیاتی، صفحات عمومی، فرم‌ها، گزارش‌ها، خروجی‌ها و تجربهٔ موبایل

## 1. جهت هنری

بهار باید در نگاه اول محصولی سازمانی، بالغ و دقیق باشد؛ نه قالب اداری قدیمی و نه داشبوردی پر از کارت‌های رنگی. شخصیت بصری از چهار لایه ساخته می‌شود:

- **هویت اختصاصی بهار:** سبز جنگلی #00825E و صورتی شکوفه #E5548B تنها رنگ‌های هویتی‌اند. سبز رنگ اقدام و اعتماد است؛ صورتی امضای ثانویه و محدود.
- **وضوح ساختاری:** سلسله‌مراتب روشن، سطوح قابل تشخیص، تایپوگرافی سنجیده، محتوای قابل اسکن و رنگ به‌عنوان معنا، نه تزئین.
- **معماری تعاملی:** قراردادهای روشن، ترکیب‌پذیری، کنترل‌های دسترس‌پذیر و رفتار استاندارد صفحه‌کلید؛ primitiveهای موجود حفظ می‌شوند.
- **حرکت کنترل‌شده:** ورود مرحله‌ای، جابه‌جایی نرم پنل‌ها، واکنش hover، انیمیشن محدود داده و عمق حساب‌شده؛ بدون تبدیل صفحات کاری به صحنهٔ نمایشی.

این‌ها منبع الهام‌اند، نه پوسته‌هایی که عیناً کپی شوند. نتیجه باید یک زبان مستقل و قابل نگهداری برای بهار باشد.

## 2. اصول محصول

1. عملیات مقدم بر تزئین: اطلاعات سریع پیدا شود و عملیات با حداقل اصطکاک انجام شود.
2. تراکم متعادل: دادهٔ کافی در یک نما، بدون فشردگی و بدون فضای خالی نمایشی.
3. یکپارچگی: یک نقش بصری = یک توکن و یک رفتار.
4. پیش‌بینی‌پذیری: رنگ، جایگاه، اندازه و رفتار کنترل‌ها در کل محصول ثابت باشد.
5. شخصیت: سبز عمیق، سطوح خنثی گرم، تایپوگرافی فارسی دقیق و جزئیات صورتی محدود.
6. دسترس‌پذیری: کنتراست WCAG AA، فوکوس آشکار، هدف لمسی حداقل 44px در موبایل و پشتیبانی reduced motion.
7. عدم تخریب: مسیرها، ماژول‌ها، مجوزها، قرارداد API، داده‌ها و گردش‌کارها با تغییر ظاهری حذف یا بازتعریف نمی‌شوند.

### قواعد مصرف

- سبز برای هر آیکون یا هر کارت مصرف نمی‌شود؛ فقط جایی که نقش معنایی دارد.
- صورتی رنگ موفقیت، خطا یا هشدار نیست.
- متن معمولی حداقل کنتراست 4.5:1 و اجزای تعاملی 3:1 دارند.
- hex مستقیم در کامپوننت ممنوع؛ رنگ از توکن مرکزی می‌آید.
- گرادیان تزئینی در جدول، فرم و داشبورد عملیاتی ممنوع است.

## 4. تایپوگرافی

- فارسی: Arad برای تیترهای نمایشی و Vazirmatn برای متن، فرم و داده.
- لاتین: Manrope.
- شناسه، کد و مقادیر فنی: monospace سیستم.
- اعداد جدولی و KPIها tabular numerals هستند.

| نقش | اندازه | وزن |
|---|---:|---:|
| عنوان صفحه | 25–32px | 650–700 |
| عنوان بخش | 18–22px | 600–700 |
| عنوان کارت | 15–17px | 600 |
| متن پایه | 14–15px | 400 |
| کنترل و جدول | 13–14px | 450–600 |
| metadata | 12px | 400–500 |
| KPI | 25–34px | 650–750 |

فاصلهٔ حروف فارسی صفر است. تیترها کوتاه و متن بدنه خوانا و با line-height مناسب باقی می‌ماند.

## 5. گرید، فاصله و تراکم

- پایهٔ فاصله 4px؛ مقیاس مجاز: 4، 8، 12، 16، 20، 24، 32، 40، 48، 64.
- عرض محتوای دسکتاپ تا 94rem؛ متن توضیحی بلند محدود به حدود 68ch.
- ساختار صفحه: Page heading → Toolbar/filters → Summary (در صورت نیاز) → Primary data surface → Secondary actions.
- کارت فقط برای گروه اطلاعاتی مستقل یا KPI معنادار؛ هر فیلد و هر ردیف نباید کارت شود.
- جدول سطح اصلی داده است و باید در صفحه از کارت‌ها اولویت بصری بیشتری داشته باشد.
- breakpointهای موجود حفظ و در 360، 390، 768، 1024 و 1440px بررسی می‌شوند.
- قابلیت‌ها و ستون‌ها در موبایل بی‌صدا حذف نمی‌شوند؛ به اسکرول افقی کنترل‌شده، فهرست ردیفی یا disclosure تبدیل می‌شوند.

## 7. معماری کامپوننت

- Button: primary, secondary, outline, ghost, destructive, link؛ اندازه‌های sm/default/lg/icon.
- Form controls: label، description، error، focus، disabled، loading و invalid.
- Table: header مشخص، ردیف قابل اسکن، تراز عددی، sorting و pagination واقعی.
- Navigation: سایدبار جنگلی تیره با active state واضح و نشانگر مکانی؛ لینک‌ها واقعی و گروه‌بندی قابل کشف.
- Card: سطح محتوایی مستقل؛ clickable بودن فقط در صورت semantics لینک/دکمه.
- Badge: فقط برای وضعیت یا طبقه‌بندی و همراه label.
- Dialog/Popover/Menu: primitiveهای Radix و مدیریت focus/keyboard حفظ می‌شوند.
- Loading/Empty/Error: ابعاد و متن پایدار؛ empty دارای اقدام بعدی معتبر؛ خطا دارای retry امن.
- Chart: palette ثابت، legend و خلاصهٔ متنی؛ رنگ تنها راه تفکیک داده نیست.

جزئیات API و معیار پذیرش در docs/component-contracts.md است.

## 8. حرکت و بازخورد

حرکت باید رابطهٔ علت و معلول را توضیح دهد، نه توجه را از کاربر بگیرد.

| حرکت | بازهٔ معمول |
|---|---:|
| hover / press | 120–160ms |
| تغییر رنگ و focus | 140–180ms |
| ورود پنل | 180–260ms |
| dialog/popover | 180–240ms |
| جابه‌جایی صفحه | 220–300ms |

الگوهای مجاز:
- fade + short translate برای ورود محتوا؛
- lift محدود 2–3px برای سطوح واقعاً تعاملی؛
- انتقال نرم state در tab، menu، dialog و drawer؛
- ترسیم نمودار و CountUp فقط وقتی فهم داده را بهتر کند؛
- scroll reveal محدود به صفحات معرفی/عمومی، نه جدول و فرم پرتراکم؛
- عمق/parallax/3D فقط برای hero یا بخش‌های بازاریابی، نه عملیات مدرسه.

الگوهای ممنوع:
- انیمیشن بی‌پایان در محیط کاری؛
- stagger روی صدها ردیف؛
- transition: all؛
- انیمیشن ضروری بدون پشتیبانی reduced-motion؛
- blur سنگین و shader در پنل عملیاتی.

## 9. RTL، چندزبانگی و تاریخ

- از logical CSS properties استفاده شود.
- زبان و جهت از پروفایل فعال کشور می‌آید؛ فرض RTL سراسری ممنوع.
- ایمیل، URL، کد، شماره و زمان با direction موضعی LTR نمایش داده شوند.
- تاریخ نمایشی از formatter مرکزی و تقویم فعال استفاده کند.
- کلیدهای ترجمه از i18n؛ متن hardcoded در کامپوننت چندزبانه ممنوع.
- ارقام نمایشی و مقادیر ارسالی به API در مرز مشخص normalize می‌شوند.

## 10. تم و دسترس‌پذیری

هر کامپوننت در Light، Dark، RTL، LTR، موبایل، دسکتاپ، keyboard-only و reduced motion بررسی می‌شود. فوکوس visible، aria semantics، label پایدار، target لمسی و کنتراست جزو تعریف Done هستند؛ نه polish اختیاری.

## 11. چاپ

چاپ surface مستقل است. رنگ و حرکت صفحهٔ وب به چاپ نشت نمی‌کند؛ header جدول تکرار، شکستن ردیف، اندازهٔ کاغذ و margin صریح‌اند. کنترل‌ها و ناوبری در چاپ مخفی می‌شوند.

## 12. معیار پذیرش تغییر

هر تغییر سیستم طراحی باید:
1. توکن یا قرارداد مشترک را اصلاح کند، نه فقط یک صفحه را؛
2. مصرف‌کنندگان اصلی را در light/dark بررسی کند؛
3. هیچ route، permission، API، field یا گردش‌کار را تغییر ندهد؛
4. lint، typecheck و build را پاس کند؛
5. dashboard، فرم، جدول، dialog، موبایل و print preview را در مرورگر بررسی کند؛
6. اگر تست بصری/مرورگر انجام نشده، صریحاً آن را به‌عنوان تست انجام‌نشده ثبت کند.


## 13. اتصال به پیاده‌سازی

پوستهٔ اصلی از hookهای معنایی پایدار استفاده می‌کند تا ظاهر به ساختار شکنندهٔ فرزندان و کلاس‌های تصادفی وابسته نباشد:

| Attribute | محل | قرارداد |
|---|---|---|
| `data-bahar-shell` | ریشهٔ پوسته | زمینه و چارچوب workspace |
| `data-bahar-sidebar` | سایدبار دسکتاپ | سطح جنگلی، گروه‌بندی و active state |
| `data-bahar-nav-link` | لینک ناوبری | hover، focus و مسیر جاری |
| `data-bahar-topbar` | هدر دسکتاپ | سطح شناور و مرزبندی |
| `data-bahar-mobile-topbar` | هدر موبایل | هدر فشرده و safe-area-friendly |
| `data-bahar-main` | ناحیهٔ محتوا | نقطهٔ ورود چیدمان صفحه |
| `data-bahar-kpi` / `data-tone` | شاخص‌ها | accent معنایی هر KPI |

مقادیر توکن‌ها در ابتدای بخش V3 فایل `src/app/globals.css` منبع حقیقت هستند. تغییر پالت باید در Light و Dark به‌صورت جفت انجام شود. کامپوننت‌ها نباید hex اختصاصی خودشان را تعریف کنند.

### Variantهای Button

کامپوننت مشترک `Button`، variantهای `default` و `primary` را برای اقدام اصلی، `secondary`، `outline`، `ghost`، `destructive` و `link` را برای نقش‌های دیگر ارائه می‌کند. variantهای خنثی نباید با hover به رنگ primary تبدیل شوند.

### قرارداد سطح‌ها

- Canvas فقط پس‌زمینهٔ workspace است.
- Surface 1 برای محتوای اصلی، Surface 2 برای ابزارها/هدر جدول و Surface 3 برای hover و انتخاب‌های ملایم است.
- Sidebar یک سطح مستقل و تیره است؛ کارت کاربر و navigation باید در همان خانوادهٔ رنگی باقی بمانند.
- سایه فقط برای تفکیک elevation است؛ border برای مرز ساختاری استفاده می‌شود.
